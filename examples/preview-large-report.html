CFT021.01Prepared Statements
EffortMediumControlPrimaryFixActorDeveloper

Use parameterized queries that bind values separately from SQL text (PreparedStatement, parameterized cursor.execute, `?` placeholders).

Language guidance (java)
JDBC PreparedStatement (built-in)
Spring `JdbcTemplate.query(sql, params, rowMapper)` parameter binding is also safe.
String sql = "SELECT * FROM users WHERE id = ?";
try (PreparedStatement ps = conn.prepareStatement(sql)) {
  ps.setLong(1, userId);
  try (ResultSet rs = ps.executeQuery()) { ... }
}
Verification
  • No SQL text is constructed by string concatenation, format strings, or template interpolation with untrusted data
  • Parameters are bound, not formatted into the query string
  • Where dynamic identifiers (table/column names) are unavoidable, they come from a server-side allowlist — not user input
Common mistakes
  • Mixing parameterization with concatenation in the same query
  • Using `LIKE` patterns that re-introduce special-character risk
References
  • OWASP SQL Injection Prevention Cheat Sheet
  • OWASP Query Parameterization Cheat Sheet

CFT021.03ORM Query Construction
EffortMediumControlPrimaryFixActorDeveloper

Use a well-tested ORM that constructs parameterized queries from object expressions.

Mapping note: Excluding ORM raw-query escape hatches.
Language guidance (java)
JPA Criteria API / Spring Data JPA derived queries / explicit parameter binding in JPQL
AVOID `@Query(nativeQuery=true)` with concatenated input.
// Derived query — safe by construction:
List<User> findByEmail(String email);
// Explicit JPQL with bind:
@Query("SELECT u FROM User u WHERE u.email = :email")
List<User> byEmail(@Param("email") String email);
Verification
  • All persistence access uses ORM expressions or parameterized queries
  • Where the ORM exposes raw-SQL escape hatches (Django `extra`, SQLAlchemy `text`, ActiveRecord `find_by_sql`), they are absent or use bound parameters
  • Dynamic table/column names come from a server-side allowlist
Common mistakes
  • Using ORM raw-query escape hatches (e.g., Django `extra`, SQLAlchemy `text`) with user input

CFT018.01HTML Entity Encoding
EffortMediumControlPrimaryFixActorDeveloper

Encode `<`, `>`, `&`, `"`, `'` (and others as required) before inserting untrusted data into HTML body context.

Mapping note: For HTML body context.
Language guidance (java)
OWASP Java Encoder (`Encode.forHtml`, `Encode.forHtmlAttribute`)
import org.owasp.encoder.Encode;
out.println("<p>Hello, " + Encode.forHtml(userName) + "</p>");
Verification
  • Every dynamic value placed into HTML output goes through an encoder
  • The encoder matches the destination context (HTML body, attribute, JS, URL, CSS — see CFT018.02/03/04)
  • Encoders come from a vetted library (OWASP Java Encoder, DOMPurify, Apache Commons Text, html-escape) — not handwritten
Common mistakes
  • Using HTML encoding for data inserted into a JS string or URL attribute (wrong context)
  • Double-encoding inputs that were already encoded

CFT018.02JavaScript Context Encoding
EffortMediumControlPrimaryFixActorDeveloper

Encode data with `\uXXXX` escapes when inserting into JavaScript string literals. Never insert untrusted data into a JS code position.

Mapping note: For JS string context.
Language guidance (java)
OWASP Java Encoder `Encode.forJavaScript`
Avoid inserting untrusted data into JS code positions entirely — prefer data attributes + DOM reads.
import org.owasp.encoder.Encode;
out.println("var name = '" + Encode.forJavaScript(userName) + "';");
Verification
  • Data inserted into a JavaScript string literal uses `\uXXXX` escaping, not HTML entity encoding
  • No untrusted data is ever placed into a JS code position (function names, identifiers, JSON.parse on attacker JSON-ish strings)
  • Where data is passed to JS, prefer `data-` attributes + DOM reads over inline injection
Common mistakes
  • Escaping for JS string context but using HTML escaping function (forward-slash, ampersand handled wrong)
  • Concatenating into a `<script>` block — even correctly escaped, breaking out via `</script>` succeeds
  • Embedding user JSON inside a JS literal with `JSON.stringify` alone — needs additional `<`/`>` escapes for safe HTML embedding
References
  • OWASP XSS Prevention Cheat Sheet
CFT018.03URL Encoding
EffortLowControlPrimaryFixActorDeveloper

Percent-encode data inserted into URL parameters, paths, or attribute values.

Mapping note: For URL parameter / attribute context.
Language guidance (java)
URLEncoder.encode(value, StandardCharsets.UTF_8)
String url = "https://api/x?q=" + URLEncoder.encode(userInput, StandardCharsets.UTF_8);
Verification
  • Data inserted into URL parameters is percent-encoded
  • Encoding library used is appropriate for the language and matches RFC 3986
Common mistakes
  • URL-encoding the value but not the query parameter name
  • Using `encodeURI` instead of `encodeURIComponent` — leaves `?`, `&`, `=` unescaped
  • Encoding twice (once at the URL layer, once at the response layer) — receiver decodes once and sees raw user input
